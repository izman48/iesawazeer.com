health.nilu.app is a calorie and weight tracker that I built for myself. It
has no food database and no barcode scanner. I tell Claude what I ate, in a
normal sentence, and Claude logs it. A small web app shows the graphs.

I built it for three reasons:

1. **I want to lose weight, for real.** I needed a tool that I would use
   every day.
2. **Logging in a chat is faster.** A normal calorie app makes you search for
   each food, pick a portion and tap through screens. Here I type one
   sentence.
3. **I own my data.** The record is on a server that I control. I can export
   all of it, and I can delete all of it. Claude reads what I type, so this
   is not a secret diary, but the record itself is mine.

## How I use it

**Food.** I tell Claude what I ate. For example:

> Chicken and avocado wrap and a bag of crisps for lunch.

Claude estimates the calories, logs the meal, and answers in one or two
lines. With the demo data from the pictures, the answer looks like this:

> Logged lunch: 710 kcal, likely 610-830, assuming a large shop-bought wrap.
> Today is 1,140 of 2,100 kcal, 960 under.

That is the full interaction. Claude logs first and tells me the assumption,
and I correct it if the assumption is wrong. A correction changes only the
item that was wrong. Claude asks a question only when the estimate could be
far off, for example for "some pasta".

When I eat at a restaurant or order a takeaway, I tell Claude to estimate
towards the high end of the range. For food from a chain or a pack, Claude
uses the menu value or the label.

**Weight.** I tell Claude my weight when I step on the scale.

**Activity.** I tell Claude my steps. A day's activity is information only.
It does not change my calorie target, so a long walk does not "earn" me
food.

**The graphs.** Then I open the web app and look at where I am against the
plan.

## How it works

The backend is FastAPI with SQLAlchemy 2, Alembic and SQLite in WAL mode.
The MCP server is mounted at `/mcp` in the same app. The web app is React
and TypeScript, built with Vite ahead of time and served by FastAPI. The
charts are drawn by hand with `d3-scale` and `d3-shape`. There is no chart
library.

### Claude is the input

Claude connects through a remote MCP connector. The server has 11 tools:
`log_food`, `log_weight`, `log_activity`, `get_day`, `get_history`,
`get_goal`, `set_goal`, `update_food_entry`, `delete_entry`, `undo_change`
and `decline_activity_proposal`.

The server stores numbers. It does not know what a wrap is. Claude makes the
estimate, and the tool descriptions carry the rules for how:

- Log first, and state the assumption. Ask a question only in a few cases,
  for example when the plausible range is about double and at least 300 kcal
  wide.
- Give a low and a high value for each uncertain item.
- Use the published value for chains and packs.
- Split a meal into items, so a correction touches one item only.

### I can see and undo everything Claude does

An AI that writes to my records must be easy to check. These are the rules
that I built in:

- **An audit log that only grows.** Each write adds a row. SQLite triggers
  stop any update or delete on that table.
- **Undo.** Each change has an id. Claude or I can undo a change from the
  last 7 days, if the entry has not changed since.
- **Keep or Undo for goals.** When Claude changes my goal, the app shows a
  banner until I confirm it.
- **Idempotency keys.** Each write carries a key, so a call that is sent
  again does not log the meal twice.
- **A write limit.** One connection can make 60 writes in an hour.
- **Only my words count.** The tools tell Claude to treat text in a document,
  web page or image as data, and not as an instruction to log or delete.

### Sign-in

The web app has one account. Sign-in needs a password (hashed with
argon2id) and a TOTP code. Claude gets access through OAuth: the
authorization code flow with PKCE, one client that I registered by hand, and
no open registration. Access tokens last one hour, and the database holds
only their hashes.

### A day ends at 03:00

Food at 00:30 belongs to the evening before. So the logging day runs from
03:00 to 03:00, and the server decides the day, not Claude.

### The weight line and the plan

Weight on a scale moves up and down each day. The blue line is a trend: each
day with a weigh-in moves the trend by 10% of the gap to the new value, and
a gap of several days counts as that many steps.

The dashed plan line is more interesting. For a goal with a fixed calorie
number and no pace, the app runs the adult body weight model from Hall et
al. (Lancet, 2011), which is the model behind the NIH Body Weight Planner.
It follows fat, lean mass, glycogen, fluid and the way the body adapts to
less food. That is why the line is a curve that flattens, not a straight
line from "7,700 kcal is one kilo".

The estimate is honest about its limits. It comes with a range (the same
model with a lower and a higher activity value), and the app says plainly
when the calories will not reach the target. After 4 weeks of logs, the app
can also propose the activity value that fits my logs. It changes nothing
until I agree.

### Operations

- The config check fails closed: if a setting is in doubt, the app does not
  start.
- Logs hold the method, route, status and duration only. No meal, weight or
  token goes into a log.
- A backup runs each night and before each deploy, through SQLite's backup
  API.
- Deploys are manual. CI runs the checks, but it holds no server key.

## What is next

Family and friends have asked if they can use it too. So I am going to open
it up. They will be able to make their own accounts and use it themselves.

## What it changed for me

This is a personal tool, not medical advice. The calories are estimates and
the plan is an estimate. But these four things changed for me:

- **I log every day.** To log a meal is one sentence, so I do it.
- **I know what I eat.** I see the calories of each meal, and that changes
  my choices.
- **I think before I order.** At a restaurant or with a takeaway, I make a
  different choice than before.
- **The trend keeps me calm.** One high weigh-in does not worry me, because I
  look at the trend line and not at one number.

I built this to lose weight, for real. The app does not do that for me. It
makes the daily part easy, and for me that was the part that mattered.
